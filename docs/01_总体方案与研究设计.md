# 0. 一页决策摘要

## 0.1 最终项目定义

本项目以 CodeScaler 的 execution-free code reward model 为基础，研究在线代码强化学习中的一个更具体、更可证伪的问题：

> **Reward Model（RM）给出高分、但代码在真实测试中失败的系统性 false positive，能否在策略更新中被提前识别和选择性纠正；在固定执行验证预算下，能否优于 RM-only 与同预算随机执行？**

项目正式名称为：

**CodeVerifier-Triage: Risk-Calibrated Selective Verification under Policy Shift for Code Reinforcement Learning**

中文名称：

**面向策略漂移的风险校准选择性验证代码强化学习**

不使用 `CURE-Code`，因为 CURE 已被用于 Coder 与 Unit Tester 协同强化学习工作；继续使用会造成命名和研究范围混淆。[R13]

## 0.2 为什么值得做

CodeScaler 已公开 1.7B、4B、8B 代码奖励模型和基于 veRL 的训练代码，并报告其可用于代码 RL 与 Best-of-N。[R1][R2] 但其失败分析同时观察到 RM 高分错误代码，并指出这类错误与代码长度、算法关键词和推理长度等表面特征相关。近期 RLVR 研究进一步显示，系统性 false positive 的危害不只取决于错误率，还取决于错误模式；策略可能持续放大可利用的 verifier 缺口。[R9][R10]

本项目不重复“训练一个更大的 RM”，也不把“不确定性大就执行”当作完整创新。它研究三个更难、也更接近线上后训练的问题：

1. **危险错误是否可预测，而不是只看全局 RM 相关性；**
2. **选择性执行产生选择性标签后，如何持续估计真实风险；**
3. **policy 变化后，静态 router 是否失效、是否被策略利用。**

## 0.3 最低可行版本与最终版本

| 层级 | 交付内容 | 是否需要在线 RL | 对求职的价值 |
|---|---|---:|---|
| Gate 0–1 | 上游复现、协议对齐、安全执行、成本审计、危险 FP 数据集 | 否 | 证明评测、数据与系统能力 |
| Gate 2–3 | group-aware 风险模型、risk–coverage、固定预算 BoN | 否 | 已可形成 Reward Model/代码验证简历项目 |
| Gate 4–6 | group-level hybrid reward、两 seed pilot、三 seed正式实验 | 是 | 形成 LLM 后训练/RLVR 强项目 |
| 论文扩展 | policy-shift benchmark、随机审计、propensity 修正、动态 router | 是 | 具备论文投稿空间 |

## 0.4 4×4090D 的可行结论

四张 24GB 显卡足以完成 1.7B policy + 1.7B RM 的完整项目，但不应原样复刻 CodeScaler 的 8B policy、8B RM、8×A100 80GB 配置。[R1][R2] 推荐顺序为：

- 离线生成：四卡各运行一个 1.7B 推理 worker；
- 离线 RM 打分：四卡并行分片；
- RL smoke/pilot：先 LoRA、group size 4、2K–4K response；
- 正式训练：根据 Gate 0 显存 profile，在“3 卡 policy + 1 卡 RM”和“四卡分阶段复用”之间选择；
- 4B 只用于最终确认，不作为前期必选项。

真正的瓶颈可能是 CPU 安全执行、磁盘和工程协议，而不是 1.7B 参数本身。

## 0.5 项目最关键的停止规则

项目不允许“先跑完整训练再判断想法是否成立”。必须按漏斗推进：

1. 危险 FP 不足或主要来自提取/截断 bug：停止原方向；
2. router 不优于 margin/random：停止复杂 UQ；
3. 固定预算 BoN 没有收益：不进入 RL；
4. reward 没有改变组内 advantage：修复，不扩大训练；
5. 两独立训练 seed 方向不一致：不做三 seed正式矩阵；
6. 最终结果未过预注册门槛：冻结负结果，不换 seed、不挑 checkpoint。

# 1. 从旧项目继承的强制设计原则

你此前的 VLM Shortcut GRPO 项目形成了三个必须固化为制度的经验：

1. 训练和离线评测的 prompt、processor、tokenizer、采样与 grader 不一致，曾制造约 26 个百分点的测量偏差；
2. 2700 个 rollout group 中约 49.85% reward variance 为零，意味着大量生成没有形成组内相对梯度；
3. CVR 工程链路完成，但 endpoint 的真实图能力下降超过预设地板，因此效果 Claim 被拒绝。

本项目由此加入以下不可绕过的规则：

- **Measurement contract 优先于方法解释。** 所有生成、提取、RM 输入、执行、评测路径使用同一冻结实现；
- **Reward 必须通过 advantage golden test。** 不能只证明 reward 数字变化；
- **零方差必须进入主账本。** 路由和 group filtering 都可能改变有效梯度比例；
- **能力、风险与成本同时报告。** 不能用一个比值掩盖能力下降；
- **独立训练 seed 与 decoding seed 分开。** 最终 claim 至少三个独立训练 seed；
- **预设门槛优先于事后叙事。** 不以挑 checkpoint、换 seed 或改阈值挽救结果。

# 2. 上游工作审计与研究缺口

## 2.1 CodeScaler：可复现基础与不可直接照搬之处

CodeScaler 的公开仓库提供：

- 1.7B、4B、8B RM；
- CodeScalerPair-51K；
- DeepCoder 数据准备脚本；
- veRL/GRPO 训练脚本；
- syntax-aware extraction 与 validity-preserving reward shaping。[R1][R2][R3][R4]

上游公开配置同时存在本项目必须先审计的四个问题：

### 2.1.1 Response 与 RM 输入上限不一致

公开训练脚本允许 policy response 最长 16384 token，但 RM `max_length` 为 4096。若代码或关键结论位于响应尾部，RM 可能只看到推理前缀；截断本身可能成为 reward shortcut。项目必须记录：

- `rm_input_tokens`；
- `rm_truncated`；
- `code_tail_visible`；
- 实际 RM 输入文本 hash；
- 截断样本的危险 FP 率。

### 2.1.2 Train 与 eval 的代码提取语义不同

公开 reward manager 在训练路径和评测路径调用不同 extractor。一个路径要求单一代码块并做 AST 检查，另一个路径更宽松地选择代码块。若不统一，训练奖励与最终执行会对同一响应读取不同程序。

本项目只能保留一个 canonical extractor，且必须被训练、离线评测、RM 输入和执行器共同调用。

### 2.1.3 KL 描述与公开脚本不完全一致

论文讨论 KL regularization 对 RM-based RL 稳定性的作用，而公开脚本默认关闭 actor KL 与 controller KL。Gate 0 只允许做一个小型双配置审计：

- repo-faithful：KL=0；
- paper-consistent：只在一个位置加入 KL。

不得同时在 reward 和 actor loss 重复计入 KL。选择后所有 arm 保持一致。

### 2.1.4 动态 group filtering 会混淆样本曝光

公开脚本启用了 group filtering。路由方法会改变全对、全错和零方差 group 的比例；如果训练框架自动重采样，两个方法即使 optimizer step 相同，也可能生成了不同数量的候选、不同 token 和不同问题曝光。

MVP 默认关闭动态 group filtering。后期若启用，必须匹配并报告：

- total generated groups；
- total candidates；
- total generated tokens；
- resample batches；
- unique problems exposed；
- effective-gradient groups。

## 2.2 RewardUQ：强 baseline，而不是自动成立的核心方法

RewardUQ 提供共享冻结 backbone 多头、LoRA ensemble、MC Dropout 和 Bayesian head。[R5][R6] 这些实现适合作为：

- disagreement 特征；
- uncertainty baseline；
- LCB/悲观奖励输入。

但 CodeScaler 是基于偏好排序训练的 scalar RM。不同 head 的 raw score 可能存在平移和缩放差异，raw variance 不能未经校准就解释为真实错误概率。因此本项目的主目标是有执行标签的事件预测，而不是抽象的“RM 不确定性”。

## 2.3 相关工作对创新边界的约束

“廉价分数 + 昂贵 verifier”的选择性验证在推理时已有理论化工作。[R12] 因而，仅做“margin 小或 variance 大就执行”不足以成为强创新。

本项目的差异化必须落在：

- **在线 policy shift；**
- **选择性标签偏差；**
- **router gaming；**
- **group-level hybrid reward；**
- **执行后是否能形成有效 GRPO 排序。**

# 3. 核心问题、定义与假设

## 3.1 候选组与执行标签

对问题 x，policy 生成 n 个候选：

`G = {y_1, ..., y_n}`

CodeScaler 给出分数：

`s_i = f_RM(x, y_i)`

安全执行器返回有限测试套件结果：

`e_i = 1[candidate y_i passes the configured test suite]`

RM top-1 为：

`i* = argmax_i s_i`

注意：`e_i=1` 只表示通过配置的测试套件，不等价于数学意义上的程序语义完全正确。

## 3.2 三个 group-level 标签

### Optimization False Positive

`z_opt = 1[e_i* = 0]`

RM 最偏好的候选执行失败。它直接反映 RM 驱动的 policy update 风险，但可能包含“组内所有候选都失败”的情况。

### Avoidable Selection False Positive

`z_sel = 1[e_i* = 0 and max_i e_i = 1]`

组内存在正确候选，但 RM 选错。它是 Best-of-N 和选择性执行能够直接纠正的错误。

### Mixed Outcome

`z_mix = 1[0 < sum_i e_i < n]`

执行后 group 内既有正确也有错误，二值 reward 能形成非零组内方差。

## 3.3 双头风险设计

只预测 `z_opt` 会把大量“全错组”路由到执行端，但这些 group 的二值执行 reward 全为 0，仍没有 GRPO 相对梯度。为避免重复旧项目的零方差浪费，推荐两类分数：

- `q_danger(G) = P(z_opt=1 | features)`：用于监控 RM 高分错误和抽样审计；
- `q_correctable(G) = P(z_sel=1 | features)`：用于优先执行可纠正 group；
- 可选 `q_mixed(G) = P(z_mix=1 | features)`：用于估计执行后能否提供梯度。

MVP 的 corrective queue 以 `q_correctable` 排序；audit queue 以 `q_danger` 分层抽样。这样既能提高执行预算的训练效用，又不会失去对全错高风险区的监测。

## 3.4 四个可证伪假设

### H1：危险高分错误可预测

RM 排名、top1–top2 margin、组内分数、提取有效性、代码复杂度、截断、隐藏表征、OOD 距离及可选 UQ disagreement，能够预测 `z_opt` 或 `z_sel`。

### H2：选择性执行优于同预算随机执行

在完全相同的候选执行数下，风险 router 比 random、margin、score dispersion 和 RewardUQ variance 捕获更多可纠正错误，并提升 BoN 选择质量。

### H3：静态 router 随 policy shift 退化

policy 从初始模型演化到中后期 checkpoint 后，代码长度、结构、错误类型和 RM exploit 行为变化，导致静态风险模型的校准或排序能力下降。

### H4：混合反馈改善在线 RL

在 matched rollout/token/execution budget 下，带随机审计和窗口校准的 hybrid feedback，相比 RM-only 与 random hybrid，改善最终 test-suite success 或降低危险错误，且不通过缩短代码、增加格式失败等方式作弊。

# 4. 系统架构

## 4.1 数据平面

离线阶段按以下顺序运行：

1. **Problem Registry**：读取冻结的问题、来源、split 和测试引用；
2. **Prompt Renderer**：只渲染可见问题，不允许测试进入 prompt；
3. **Policy Generator**：按固定 group size、seed 和采样配置生成；
4. **Canonical Extractor**：从 raw response 得到唯一 executable code；
5. **CodeScaler Adapter**：保存 raw score、softplus score、实际 RM 输入和截断信息；
6. **Sandbox Executor**：执行所有候选并缓存；
7. **Label Builder**：构造 candidate/group 标签；
8. **Feature Pipeline**：只生成 pre-execution 特征；
9. **Risk Trainer/Calibrator**：train/calibration/dev 严格分离；
10. **Routing Simulator**：在固定 candidate-execution budget 下评估。

## 4.2 在线 RL 控制平面

MVP 使用整组路由：

- selected group：所有候选进入执行器；
- unselected group：所有候选使用 CodeScaler；
- 同一 group 不混合不同 reward 类型；
- 低风险未选组仍保留 5%–10% 分层随机审计；
- router 在一个训练窗口内冻结，只允许窗口之间重校准；
- 每个 route decision 记录 propensity 和 router revision。

## 4.3 为什么先做 group-level routing

若同一 group 中部分候选用 binary execution、部分候选用 scalar RM：

- reward 语义不同；
- 尺度和方差不同；
- 路由本身可能改变 advantage 排序；
- 很难区分收益来自 oracle 信息还是 reward scale。

整组路由使组内奖励语义一致，更适合 GRPO，并显著降低实现和归因风险。

# 5. 数据、切分与泄漏防护

## 5.1 数据来源

主训练问题使用 pin revision 的 DeepCoder Preview Dataset。其公开数据卡描述了 TACO Verified、PrimeIntellect synthetic verified problems 和 LiveCodeBench v5 子集。[R8]

CodeScalerPair-51K 只用于：

- 理解上游 preference construction；
- 可选 hard-negative 初始化；
- 与新鲜 on-policy 数据做分布比较。

它不能作为本项目唯一的风险校准数据，因为它来自不同 policy 和历史分布。

## 5.2 新鲜 on-policy 语料规模

第一轮：100 prompts × 4，用于协议 smoke。

第二轮：500 prompts × 4，用于 prevalence 和简单 baseline。

目标规模：1500–2500 prompts × 4，即约 6000–10000 个候选。比固定数量更重要的停止条件是：

- 至少约 200 个危险 FP group；
- 来源不集中于一个子集；
- 不是主要由提取、RM 截断或执行器错误造成。

若无法满足，应停止 risk-router 主线，而不是强行训练复杂模型。

## 5.3 Problem-level split

切分单位必须是 `problem_hash`，不能按 candidate 或 preference pair 随机切分。推荐：

- risk train：60%；
- risk calibration：20%；
- risk dev：20%；
- RL train/dev/final：使用独立冻结注册表；
- final test 在 Gate 6 前密封。

所有同题候选、不同 checkpoint 输出和衍生 pair 必须在同一 split。

## 5.4 测试用例隔离

测试只允许存在于 execution backend 的受控字段。下列位置不得包含测试：

- policy prompt；
- RM 输入；
- router feature；
- W&B 可见样例；
- Agent 日志；
- Git 仓库中的公开 artifacts。

必须有自动化 `test_prompt_no_leakage.py`，扫描 rendered prompt 和特征列。

# 6. 代码提取与 RM 评分合同

## 6.1 Canonical extractor

MVP 规定：

- 允许代码块之前存在 reasoning；
- 最终响应必须恰好包含一个 Python 或无标签 fenced code block；
- 多代码块、空代码块、未闭合 fence、AST 失败分别返回明确状态；
- 只做换行和首尾空白规范化，不重写程序语义；
- raw response 永久保留。

该规则可能降低初始有效率，但能消除 train/eval 分歧。格式 reward 是否加入，必须作为独立变量并保持所有 arm 一致。

## 6.2 RM 输入模式

不能凭印象决定 CodeScaler 看“完整 CoT”还是“问题 + 提取代码”。Gate 0 应比较：

1. 上游真实训练路径所构造的输入；
2. README 示例的 question + program；
3. 对 100–1000 个候选的 rank correlation、截断率和 FP 切片。

最终冻结一种 `input_mode`。每条分数保存实际渲染文本 hash，避免以后 tokenizer/template 更新造成静默漂移。

## 6.3 长度决策

初始 generation cap 为 2048，但这不是永久值。Gate 0 检查：

- 响应触顶比例；
- 提取代码是否完整；
- RM 输入是否截断；
- 2048/3072/4096 对有效率和 base pass 的影响。

若 cap-hit 超过约 5% 或代码尾部经常缺失，则上调；一旦冻结，所有 arm 使用相同上限。

# 7. 执行 Oracle 与安全边界

## 7.1 Oracle 语义

必须区分：

- `train_suite_pass`：用于训练 reward 的测试套件；
- `audit_suite_pass`：未参与当前 reward 的审计测试；
- `final_suite_pass`：最终冻结 evaluator；
- `semantic_correctness`：有限测试无法证明，不作为项目 Claim。

对于 `INFRA_ERROR`、执行服务崩溃、容器拉取失败、测试解析错误：

- 不得视为错误答案；
- 需要重试或从该次训练/统计中剔除；
- 必须单独报告 infra error rate。

## 7.2 安全要求

SandboxFusion 是候选执行后端，但公开 issue 显示配置、内存限制、stdout 截断和运行稳定性等需要自行验收。[R7] 必须做到：

- 独立 Linux 服务或 VM；
- 无网络、非 root、只读 rootfs；
- tmpfs workdir；
- cgroups v2 限制 CPU、内存、swap、PID；
- wall-time 后杀死整个进程树；
- 限制 stdout/stderr、文件大小和磁盘；
- 不挂载项目源码、模型、密钥；
- 镜像使用 digest，不只使用 tag；
- WSL2 或普通 Docker 本身不被视为足够的强安全边界。

## 7.3 安全验收样例

至少覆盖：无限循环、fork bomb、内存炸弹、巨量输出、磁盘填充、网络连接、读取 `/proc`、子进程树、signal abuse、递归、长时间 sleep。每次测试后服务必须恢复健康。

# 8. 风险模型设计

## 8.1 从简单模型开始

固定顺序：

1. top1–top2 margin；
2. group score dispersion；
3. syntax/static-analysis heuristic；
4. Logistic Regression；
5. GBDT；
6. frozen RM embedding + MLP；
7. RewardUQ 多头 variance；
8. 最终 group-aware calibrated router。

复杂模型只有在明显超过简单 baseline 时才保留。

## 8.2 特征组

可用特征：

- RM：top1、top2、margin、mean/std、rank entropy；
- validity：代码块、AST、compile、入口函数；
- length/complexity：response/code token、行数、函数、分支、import；
- truncation：RM token 数、是否截断、代码尾部可见；
- representation：冻结 hidden embedding、OOD distance；
- optional UQ：head variance、rank disagreement；
- diversity：候选重复率、token/AST 相似度。

禁止特征：执行状态、通过测试数、测试输出、隐藏测试、route 后产生的信息。

## 8.3 防止 router 只学表面 shortcut

必须完成：

- 长度匹配子集；
- 移除长度/复杂度特征；
- source-held-out；
- checkpoint-held-out；
- RM 截断切片；
- 对高置信低风险 FP 的人工分析。

若复杂 router 的收益在移除长度后消失，应如实定义为“长度风险规则”，不包装成通用不确定性模型。

## 8.4 校准和类别不平衡

危险 FP 可能较少，因此：

- 主指标使用 PR-AUC、recall@budget、precision@k；
- AUROC 只作辅助；
- 校准只在 calibration split 做 Platt 或 isotonic；
- dev 只用于模型和阈值选择；
- final 不校准。

# 9. Router、随机审计与选择偏差

## 9.1 固定执行预算

预算单位是 **候选执行次数**，不是 group 数。MVP 固定 group size=4；执行一个 group 即消耗 4 次候选执行。

评估预算点：10%、25%、50%、100%。所有方法严格执行相同数量候选。

## 9.2 两条队列

- Corrective queue：按 `P(avoidable_selection_fp)` 排序，目标是纠正能产生相对信号的 group；
- Audit queue：按 `P(optimization_fp)` 和 risk decile 分层随机抽样，目标是监测 RM 与 router 的盲区。

随机审计占未选 group 的 5%–10%，并计入总预算。

## 9.3 Propensity 与总体风险估计

只执行高风险组会产生 selective-label bias。每个 group 必须记录：

- `route_probability`；
- `route_reason`；
- `risk_decile`；
- `audit_flag`；
- `router_revision`；
- `policy_checkpoint`。

总体风险可使用逆概率加权估计，并同时报告未加权 selected slice。为控制方差，inverse propensity 需要预注册裁剪上限。

## 9.4 Router gaming

policy 虽然看不到 route decision，但 reward 机制依赖生成特征，仍可能学会：

- 生成 RM 高分且 router 判低风险的错误代码；
- 通过缩短/格式化规避执行；
- 利用早期 router 的分布盲区。

缓解策略：

- router 按训练窗口冻结；
- 低风险随机审计永不归零；
- checkpoint 分层校准；
- 监控每个 risk decile 的真实 FP；
- final 对静态 router 和动态 router 直接比较；
- 不把 router risk score暴露给 policy prompt。

# 10. Hybrid reward 与 GRPO 实现

## 10.1 MVP reward

整组被执行：

`r_i = e_i`

整组未执行：

`r_i = softplus(s_i)`，无效/空代码为 0。

同组不混 reward 类型。

## 10.2 全对/全错执行组

若执行结果全 0 或全 1，二值 reward 组内方差为零。MVP：

- 该 group 不参与 policy update；
- 仍记录到 exposure ledger；
- 报告 all-pass、all-fail、execution-zero-variance；
- 不自动回退到高风险 RM 排序。

后期可以消融 lexicographic tie-break：`e_i + epsilon * normalized_rm_score`，但必须证明任何通过候选始终高于失败候选，且不能作为默认结果。

## 10.3 Golden advantage tests

至少构造：

- mixed execution group；
- all-pass；
- all-fail；
- RM score mixed group；
- router disabled；
- INFRA_ERROR；
- score affine transform；
- group ordering permutation。

测试必须证明：

- router disabled 时精确退化上游；
- 新 reward 在应变化时改变组内 advantage；
- uniform group 明确 skip；
- 样本顺序不改变结果；
- 不产生 NaN。

# 11. 算力、资源与运行方式

## 11.1 硬件清单与最低条件

推荐：

- 4×4090D 24GB；
- 16 CPU cores/64GB RAM 最低，32 cores/128GB 更合适；
- 500GB 空闲磁盘最低，1TB 更稳；
- Ubuntu + ext4/XFS；
- Docker/cgroups v2；
- 可靠散热和长跑监控。

4090D 无 NVLink 假设，必须用 `nvidia-smi topo -m` 和 NCCL smoke 实测 PCIe 拓扑。消费级卡无 ECC，应记录 Xid、温度和异常重启。

## 11.2 资源模式

### Offline generation

四卡各一个独立 1.7B worker，按 problem hash 分片。这样比强行 tensor parallel 更适合小模型。

### Offline RM scoring

四卡各加载 CodeScaler-1.7B，批量分片；保存 batch size、吞吐、最大显存。

### Integrated RL

优先尝试：3 卡 policy/rollout + 1 卡 RM，LoRA 或 FSDP/offload。若框架耦合导致 OOM/死锁，使用 sequential fallback：四卡先生成，释放 rollout engine，再打分/执行，再四卡 policy update。

### 4B confirmation

只有 1.7B 核心结论成立后，才做少量 4B 确认。不得用 4B 扩大整个 baseline 矩阵。

## 11.3 成本审计

Hybrid 系统总成本：

`C_hybrid = C_policy + C_RM + C_router + C_selected_execution`

Full execution：

`C_full = C_policy + C_all_execution`

本地已有测试的执行可能比 1.7B RM 推理更便宜。因此 Gate 0 必须实测：

- GPU-seconds；
- CPU core-seconds；
- wall-clock p50/p95；
- 并发吞吐；
- timeout/infra rate；
- 每个成功样本成本。

若 RM + router 开销不小于节省的执行成本，不得声称“加速”；项目主叙事改为“有限 Oracle budget 下的可靠性”。

# 13. 指标与统计协议

## 13.1 离线主指标

- optimization FP rate；
- avoidable selection error；
- selection regret；
- PR-AUC；
- recall at execution budget；
- risk–coverage、AURC、eAURC；
- BoN@4/8 fixed-budget accuracy；
- calibration Brier/ECE。

## 13.2 在线主指标

- sample accuracy；
- task pass-any@4；
- task pass-any@8；
- 明确定义的 pass-all@k（若报告）；
- 最终 benchmark 分项。

不得把 pass-any、pass-all、HumanEval estimator 混用。

## 13.3 诊断指标

- RM–execution disagreement；
- executed group 与 random audit 比例；
- dangerous FP by checkpoint/risk decile；
- all-pass/all-fail/zero-variance；
- effective-gradient group ratio；
- generated groups/candidates/tokens；
- policy KL；
- invalid/fragment/compile error；
- response/code length；
- RM truncation；
- router calibration drift。

## 13.4 统计

- resampling unit：problem；
- paired bootstrap：10000 次，95% CI；
- 关键 final arm：至少 3 个独立训练 seed；
- 同时报告每个 seed、mean/std 和 problem-level CI；
- checkpoint 选择规则预注册；
- final test 只运行一次；
- 绝对百分点与相对提升分开。

# 14. Gate 与 Go/No-Go 标准

## Gate 0：协议、安全、成本与复现

通过：上游可运行；统一 extractor；RM 输入/截断冻结；沙箱通过安全验收；evaluator parity；明确主 claim 是 cost 还是 reliability。

## Gate 1：问题是否真实

建议通过条件：

- 新 policy rollout 危险 FP 率约不低于 5%；
- 危险 FP group 至少约 200；
- 不主要由 extractor、truncation 或 infra bug 造成；
- 不只集中于单一来源。

## Gate 2：离线路由是否有效

建议通过条件：

- 同执行预算相对 random 捕获危险 FP 提升约 20% 或更强；
- 显著优于 margin；
- 在至少两个 shift slice 方向一致；
- paired problem bootstrap CI 支持。

## Gate 3：是否值得进入 RL

满足以下之一：

- 同预算 BoN 提升约 1–2pp；
- 正确率下降不超过 0.5pp 时执行减少约 30%；
- 接近 execute-all 的选择质量但显著少执行。

## Gate 4：RL 实现可信

- reward/advantage golden tests 全过；
- 20–30 step 无 NaN/OOM/死锁；
- router 不退化为 execute-all/none；
- exposure、预算和 route trace 完整。

## Gate 5：两 seed pilot

- P6 相对 P2/P4 方向一致；
- 能力无明显退化；
- dangerous FP、最终通过率或成本至少一项有明确改善；
- 无缩短代码/增加格式错误的作弊迹象。

## Gate 6：正式结果

- 3 独立训练 seed；
- 关键四 arm；
- matched budget；
- 一次 final；
- claim ledger 与证据索引完整。

# 16. 风险与转向路线

## 16.1 执行比 RM 更便宜

取消“节省延迟” Claim，保留有限 oracle feedback/reliability 叙事。若没有 oracle scarcity 的真实场景，则转向 RM 修复。

## 16.2 危险 FP 不足

说明 CodeScaler 在目标 1.7B policy 分布上已足够可靠。可以：

- 使用早期 RM-only RL checkpoint 生成更 on-policy 的候选；
- 选择中等难度题；
- 若仍不足，停止 router 项目。

## 16.3 Router 不优于 margin

采用 margin 作为最终 router；项目重点改为在线校准与策略漂移。若连 margin 也无价值，转 Hard-Negative CodeScaler Repair。

## 16.4 离线有效、在线无收益

保留 executed corpus、风险审计、BoN 与 shift 分析，形成 Reward Model evaluation 项目；不声称改善 RL。

## 16.5 执行组零方差过多

优先使用 `q_sel/q_mix` 选择可纠正 group；若 effective-gradient ratio 仍低，考虑 lexicographic tie-break 消融，或转为 risk-regularized RM：

`r_safe = softplus(s) - beta * q_danger`

## 16.6 Router gaming

提高随机审计、缩短冻结窗口、加入 checkpoint-held-out 训练；若仍恶化，回退 full execution 或 static pessimistic reward。

## 17.1 强简历版本

结果产生前只保留占位：

> 基于 CodeScaler/veRL 构建策略漂移下的风险校准选择性验证 RLVR 管线，针对 RM 高分但执行失败的系统性 false positive 训练 group-aware 双头 router，并通过分层随机审计与 propensity 账本监测选择性标签偏差；在固定候选执行预算、matched rollout/token 和 3 个独立训练 seed 下，将 top-1 false-positive 降低 **X%**，使 Qwen3-1.7B 代码 test-suite success 提升 **X.Xpp** / 或在非劣能力下减少执行 **X%**。

只有 Gate 6 支持后才能填数字。

## 17.2 面试主线

1. 为什么 CodeScaler 的全局性能不排除高分系统性错误；
2. 为什么只预测 top1 错误会浪费在 all-wrong group；
3. 为什么使用 corrective + audit 双队列；
4. 如何避免 selective-label bias 和 router gaming；
5. 如何做 extractor/RM truncation/sandbox/evaluator contract；
6. 为什么 matched budget 必须包含动态 group filtering 和样本曝光；
7. 负结果时如何按 Gate 转向。

## 17.3 论文方向

论文题目可围绕：

**Selective Oracle Feedback under Policy Shift for Code Reinforcement Learning**

需要在强简历版本之上增加：

- 多 checkpoint policy-shift benchmark；
- 静态 router 失配的系统性证据；
- propensity-aware population risk；
- dynamic router 相对 static 的明确提升；
- 至少另一种 code RM 或 policy scale；
- random noise 与 systematic FP 的受控对比；
- router gaming failure analysis。

简单的“variance 高则执行”不构成论文贡献。

# 18. Agent 实施原则摘要

- 任务入口是 `tasks/task_graph.yaml`，不是口头计划；
- 每个 Task ID 一个 commit/PR；
- Agent 不能自行批准 Gate、训练或 final test；
- 先测试后实现；
- 冻结 contract 修改必须走 change request；
- 所有 run 使用 manifest、hash 和 evidence index；
- GPU 训练前必须有明确预算授权；
- 安全、泄漏、协议错配、reward no-op 是立即停止条件；
- 最终产出是证据链，不是只有一张最好看的曲线。
