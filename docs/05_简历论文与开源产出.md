# CodeVerifier-Triage：简历、面试、开源与论文路线

# 1. 简历阶段划分

## Gate 2 版本

可写“构建代码 RM 风险审计和固定预算选择性验证”，不能写“改善 RL”。

## Gate 3 版本

可写“同预算下改善 BoN/降低验证次数”，必须同时写能力地板和执行预算。

## Gate 6 版本

可写在线 RL 结果，但必须是三独立训练 seed、matched budget 和 final evidence。

# 2. 简历条目模板

> 基于 CodeScaler/veRL 构建策略漂移下的风险校准选择性验证代码 RL 管线；针对 RM 高分但执行失败的系统性 false positive，设计 group-aware 危险度/可纠正性双头 router，并通过分层随机审计与 propensity 账本监测选择性标签偏差；在固定候选执行预算与 matched rollout/token 下，相比 RM-only 和 random hybrid 将 **[主指标]** 改善 **[数字]**，并在 3 个独立训练 seed 上完成复现。

没有最终数字时不得填入估计值。

# 3. 面试故事

1. 上游为何不能直接复现：response/RM 长度、extractor、KL、filtering；
2. 为什么高分错误比一般 UQ 更重要；
3. 为什么 top1-wrong router 会浪费 all-wrong group；
4. 双头 router 与随机 audit；
5. selective-label bias 与 propensity；
6. router gaming；
7. 4×4090D 下的资源调度；
8. 何时停止并转向 RM repair。

# 4. 开源交付

推荐发布：

- clean-room adapters / patch files；
- contracts、schemas、task graph；
- 不含测试正文的元数据和衍生统计；
- risk/BoN evaluator；
- synthetic golden tests；
- 技术报告；
- 可选匿名/许可允许的 failure corpus。

不默认发布：上游未明确许可源码复制、原始测试、模型权重、完整候选代码语料。

# 5. 论文主张

论文核心不应是“UQ routing”，而是：

> 在 on-policy code RL 中，选择性 Oracle feedback 既面临 policy shift，也面临 selective labels；如何用 group-aware corrective routing、持续随机审计和 propensity-aware risk estimation 控制系统性高分错误？

# 6. 论文必要实验

- 静态 router 在 base/early/mid/late checkpoint 的退化；
- random audit 与无 audit；
- propensity correction；
- dynamic vs static；
- systematic FP vs random noise；
- 至少另一 code RM 或 4B policy；
- 真实代码 benchmark；
- router gaming/failure taxonomy；
- 三 seed正式 RL。

# 7. 诚实边界

- 测试通过不是语义证明；
- 本地执行成本不一定高于 RM；
- 一个 benchmark 的提升不代表通用 Code LLM；
- router 的概率不是分布外保证；
- conformal/校准保证依赖分布假设，policy shift 下需重新验证；
- 未过 Gate 的 Claim 标记 NOT_TESTED 或 REJECTED。
